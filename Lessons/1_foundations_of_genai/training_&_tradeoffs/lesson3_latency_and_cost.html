Latency and Cost: Why Bigger Isn't Always Better

Lessons 1 and 2 covered how models are trained and how much text they can see at once. This lesson is about the decision you face every time you pick a model: how fast will it respond, and how much will it cost?

Before your assignment — and before building anything real — you need a framework for matching model size to task complexity. The smartest model is rarely the right default.

1. What Is Latency?

Latency is the time between sending a prompt and receiving a useful response. Users feel it immediately: a chatbot that pauses for 5 seconds before every reply feels broken, even if the answer is perfect.

Latency has two main components:

  • Time to first token (TTFT): how long before the model starts streaming output. This covers reading your prompt, running the forward pass, and beginning generation.
  • Tokens per second (throughput): how fast tokens arrive after the first one. A long answer at 20 tokens/sec feels much slower than the same answer at 80 tokens/sec.
Total wait ≈ TTFT + (output tokens ÷ tokens per second). A 500-token reply at 50 tok/s adds ~10 seconds after TTFT. Short prompts to small models feel snappy; long prompts to huge models do not.

Bigger models are slower because each generated token requires more matrix math across more parameters. A 7B-parameter model on a laptop might feel instant; a 405B frontier model on shared cloud GPUs might take seconds before the first word appears.

2. What Drives Cost?

Most hosted LLM APIs charge per token. From Lesson 2: tokens are the billing unit, not words or characters.

  • Input tokens — your prompt, system message, retrieved documents, chat history
  • Output tokens — everything the model generates
Cost per request ≈ (input tokens × input price) + (output tokens × output price)

Output tokens usually cost more than input tokens — generating each new token requires a full forward pass and sampling step, while reading input is a single pass. On Claude Sonnet 4.6, for example, output is priced at $15/M tokens vs. $3/M for input — a 5× premium.

Bigger, more capable models cost more per token than smaller ones. GPT-4o mini might cost $0.15/M input; Claude Opus 4.6 costs $5/M input — over 30× more for the same token count.

3. The Core Tradeoff: Quality vs. Speed vs. Cost

You rarely get all three. The mental model is a triangle — push toward one corner and the others suffer:

  • Tiny model: fast, cheap, but more errors on hard tasks
  • Huge model: slow, expensive, but much more capable and reliable on complex work
  • There is no free lunch — "best model for everything" does not exist

4. Matching the Model to the Task

The assignment skill — and the production skill — is right-sizing:

Task typeComplexityTypical tierWhy
Sentiment classification, date extraction, spam filterLowSmall / miniPattern is simple; errors are cheap to catch; volume is high
Summarization, Q&A over docs, email draftingMediumMedium (Haiku / Sonnet)Needs coherence but not deep reasoning chains
Multi-step reasoning, code generation, research synthesisHighLarge / frontierMistakes compound; quality matters more than marginal cost

Real companies often run a mix: a cheap model triages or filters millions of requests; an expensive model handles only the hard cases that pass through. This is called a cascade or router pattern.

5. Local Models vs. API Models

Your assignment will likely use open-source models running locally (e.g., smaller Llama or GPT-2 variants). Hosted APIs are the other path. Both are valid — they optimize different corners of the triangle.

Local (self-hosted)

  • No per-token API bill — you pay for hardware and electricity
  • Needs a capable GPU/CPU; big models may be impractical on a laptop
  • Can be slower than optimized cloud inference
  • Full control over data — nothing leaves your machine
  • Great for learning, prototyping, and privacy-sensitive work

API (OpenAI, Anthropic, Hugging Face Inference)

  • Pay per use — no upfront GPU purchase
  • Access to frontier models you could not run locally
  • Provider handles scaling, uptime, and optimization
  • Data sent to a third party — check privacy policies
  • Usually faster and more capable than local on consumer hardware

6. Why This Matters for Real Products

At scale, small per-request differences become enormous:

1 million requests/day × $0.002 extra per request ≈ $2,000/day ≈ $60,000/month

A spam filter processing 10 million emails daily cannot afford frontier-model pricing on every message. A legal research tool handling 50 complex queries per day can afford Opus — because volume is low and mistake cost is high.

Product teams constantly ask: "Do we need the smartest model, or does a cheaper one work well enough?" The answer is almost always task-dependent — which is why this framework matters before you write your first API call.
