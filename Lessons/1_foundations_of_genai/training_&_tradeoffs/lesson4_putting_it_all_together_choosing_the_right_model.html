Putting It Together: Choosing the Right Model

Lessons 1–3 covered three pillars of real-world LLM decisions: how models are trained, how much context they can see, and what speed and cost you pay. This lesson ties those threads into one practical framework — the same kind of thinking you'll use in the upcoming hands-on assignment.

Before the assignment: You will fine-tune a model, track experiments, and compare runs. This page is your cheat sheet for why those choices matter — not just how to click through a notebook.

1. Three Questions to Ask Before Choosing a Model

Every product decision starts with constraints. Before you pick "GPT-4" or "fine-tune Llama" by default, run through these three questions:

QUESTION 1

How much context do I need?

Short prompts (a tweet-length question, a single email) fit easily in any modern model — even 8K-token windows are plenty.

Long documents (full contracts, codebases, multi-turn chat history) need a model with a large context window and budget for all those input tokens. From Lesson 2: stuffing 100 pages into the prompt is expensive and slow even when it technically fits.

Rule of thumb: retrieve or summarize first; only send what the model must see.

QUESTION 2

How fast does this need to respond?

Real-time chat (customer support, copilots in the IDE) needs low latency — usually a smaller or mid-tier model, streaming output, and short replies.

Batch / overnight jobs (summarizing thousands of tickets, labeling a dataset) can tolerate slow, frontier models because nobody is staring at a spinner.

From Lesson 3: latency = time to first token + (output length ÷ tokens per second). Pick model tier accordingly.

QUESTION 3

How complex is the task?

Simple classification or extraction ("Is this email spam?", "Pull the invoice date") often works with a small model + clear prompt — or even a non-LLM baseline.

Deep reasoning, multi-step planning, rare domain expertise (legal analysis, complex debugging, nuanced writing) may need a larger model — but verify with evals before assuming you need the biggest one.

Don't use a sledgehammer for a thumbtack. Start small, measure, escalate only when metrics justify it.

QuestionLean smaller / cheaper when…Lean bigger / fine-tuned when…
Context Prompts stay under a few pages; you summarize long sources You truly need full-document reasoning in one shot
Speed Interactive UI, high QPS, mobile users Offline batch, quality beats wait time
Complexity Structured labels, templates, narrow formats Multi-hop reasoning, novel domain jargon, strict style

2. Base Model vs. Fine-Tuned — When Do You Need Which?

From Lesson 1: a base model (or a general instruction-tuned API like ChatGPT) already absorbed broad language knowledge during pretraining. A fine-tuned model gets extra training on your examples to specialize behavior.

Default stance: If a general-purpose model already passes your evals with good prompting, don't fine-tune. Fine-tuning costs data, compute, and ongoing maintenance. Prompt engineering + retrieval is cheaper to iterate.

Fine-tuning makes sense when:

  • You need a very specific style or format (brand voice, JSON schema, medical note template) that prompting alone can't stabilize
  • You have domain knowledge the base model rarely saw (internal acronyms, proprietary procedures, niche regulations)
  • You need consistent behavior on a narrow task at scale — same input pattern, same output structure, every time

Stick with a base / API model when:

  • The task is general Q&A, brainstorming, or summarization of public topics
  • Your requirements change weekly — prompts update in minutes; retraining does not
  • You lack enough high-quality labeled examples (rough rule: hundreds to thousands for meaningful SFT, not five examples)

3. What Fine-Tuning Looks Like in Practice

Fine-tuning is not mysterious — it's the same gradient-descent loop from Lesson 1, just on a small curated dataset and for far fewer steps than pretraining.

  1. Prepare a dataset of input/output pairs for your task. Example: customer message → ideal support reply. Clean, consistent formatting matters more than raw size.
  2. Choose a starting checkpoint — a pretrained or instruction-tuned base (e.g., Llama, Mistral, GPT fine-tuning API). You are nudging weights, not training from scratch.
  3. Train with small learning rates for a few epochs. Updates are tiny compared to pretraining — you don't want to "forget" general language ability (catastrophic forgetting).
  4. Evaluate on a held-out set you did not train on. Did accuracy, F1, human ratings, or task-specific metrics improve vs. the base model with prompts?
  5. Log everything — hyperparameters, loss curves, eval scores — so you can compare runs and reproduce what worked.
PhasePretraining (Lesson 1)Fine-tuning (your assignment)
DataTrillions of web tokensHundreds–thousands of curated pairs
DurationWeeks–monthsHours–days
Weight changesLarge, from random initSmall nudges on a capable base
Success metricLow general lossHigh score on your task eval

Fine-tuning involves lots of trial and error: learning rate too high → model diverges; too low → no improvement; too many epochs → overfits your tiny set. That is why experiment tracking is not optional — it is how professionals remember what they already tried.

4. Introducing Weights & Biases (W&B)

Weights & Biases (W&B) is an experiment-tracking platform used across industry and research. When you fine-tune in the assignment, you'll log runs to W&B and see dashboards like the mockup below.

What W&B tracks for you:

  • Loss curves — training (and validation) loss over steps; should generally trend down unless something is wrong
  • Hyperparameters — learning rate, batch size, epochs, model name — attached to each run automatically
  • Side-by-side comparisons — overlay multiple runs to see which settings won
  • Artifacts & notes — checkpoints, eval tables, free-text "changed prompt template v2"

Why this matters: your first fine-tune will probably underperform. Your fifth might win — but only if you can remember what changed between them. Spreadsheets and memory don't scale; W&B does.

W&B is standard in real ML workflows — not just coursework. The habit of "log first, argue from curves later" saves teams from mistaking luck for skill.
